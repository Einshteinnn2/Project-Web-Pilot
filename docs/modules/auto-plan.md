# AutoPlan — автовыполнение текущего плана

AutoPlan разрешает Web Pilot продолжать план выбранного проекта. Sequential отправляет одно «Продолжай» основному чату на подходящей паузе; с 0.6.114 обычный Chat при ON может автоматически сменяться после заданного количества подтверждённых микрозадач. Parallel создаёт отдельные чаты/worktree и принимает проверенные интеграции; основной чат не выполняет обычные задачи в main. Конфликт или падение объединённого теста при ON автоматически передаётся основному чату один раз; отдельной кнопки нет. Ошибка запуска проверки требует исправления окружения, не кода агентом. Протокол очереди — [parallel-execution](parallel-execution.md).

## Разрешение

AutoPlan и Review независимы между собой и между проектами. Пользователь управляет ими кнопками карточки проекта, текст агента режимы не меняет. ON зелёный с aria-pressed=true в обеих темах; во время действия панели кнопка временно недоступна.

По умолчанию OFF. Одно явное ON до первого плана сразу отображается и сохраняет ожидание публикации; неподтверждённые `NONE`/Review/транзакция не разрешают Send, но не выключают ON. При публикации первого подтверждённого ACTIVE scope разрешение связывается с origin из плана (не с чатом, нажавшим кнопку), а после завершения текущего ответа ассистента начинает выполнение без второго клика. OFF отменяет ожидание. Restart сохраняет выбор только своего проекта. Два PlanMonitor разных основных чатов не владеют выбором: stale `null`, ошибка чтения и устаревшая revision приостанавливают Send, но не снимают ON и не откатывают ранее подтверждённый scope.

Хранение: settings.json, projectAutoPlan[workspace] = {projectId,scopeId,enabled,sessionId,sessions,awaitingPlan,offReason,planRevision,previousScopeId,handoff}. Ожидание первого плана имеет scopeId="" и awaitingPlan=true. planRevision не допускает отката к более старому плану; previousScopeId защищает от повторного связывания старого архивированного scope. Старое глобальное autoPlanEnabled игнорируется. Подтверждённое завершение сохраняет OFF с offReason=`complete`; уже подготовленное финальное поручение основной сессии остаётся разрешённым. Только пользовательское OFF присваивает `manual`; программный `flow.disable()` показывает `AUTHORIZATION_OFF`, не `MANUAL_OFF`. Следующий scope начинает с OFF. Staged DONE и транзакция не подтверждают завершение. Ошибка чтения запрещает Send/назначение, но не стирает авторизацию.

sessions[sessionId] содержит отдельные autoPlanCheckpoint/automationCheckpoint и `chatTaskCursor` без текста беседы. Защита Review/AutoPlan от повторной отправки сохраняется при смене scope; UNKNOWN не повторяется.

Разрешение проверяется по projectId из зарегистрированного проекта. Другой projectId в той же папке начинает с OFF и пустыми журналами. Старая запись без projectId допускается только для прежнего зарегистрированного Session ID. Окончательное удаление очищает разрешение и checkpoints; архивирование сохраняет их. При старте убираются записи отсутствующих проектов и устаревшие адреса отправки; UNKNOWN существующего проекта сохраняется.

## Контроллеры

project-auto-plan.mjs хранит проектное разрешение; project-session-auto-plan.mjs создаёт AutoPlan, AutomationSendState и PlanMonitor каждого основного runtime, но per-chat view не вправе менять project-level scope без подтверждённого плана. Скрытые чаты адресуются самостоятельно; другой выбранный проект не переносит отправку. Для sequential-плана явное OFF и последующее ON **в другом основном Chat или Work после Recovery** привязывает незавершённый scope к этой новой сессии, сохраняя ledger прежней. Смена выбранного чата сама по себе разрешение не передаёт; старый основной чат после передачи не отправляет «Продолжай». Для parallel-плана переключение не перехватывает main: очередь подтверждает scope через Kit и передаёт результаты origin, сохранённому в плане. Исполнители наследуют разрешение родителя; Review и собственный программный disable исполнителя его не выключают.

main.mjs связывает защищённый pilot:auto-plan с чтением плана, сохранением и событиями; ui/sidebar.mjs — с кнопкой. При ON IPC повторно проверяет projectId, scope/состояние Kit и неизменность выбранного проекта/чата; проверенный NONE создаёт ожидание, временно неподтверждённое чтение сохраняет последнюю доверенную привязку, а ACTIVE разрешает последовательной сессии немедленно пересмотреть уже наблюдаемую idle-паузу. События последующей публикации, Recovery, загрузки истории, busy→idle и очистки черновика пробуждают тот же ON без OFF→ON. auto-plan-state.mjs проверяет план, транзакцию и Review; auto-plan.mjs управляет продолжением, Composer отправляет. Функционального polling и model API нет.

### Ротация Chat по микрозадачам (0.6.114)

- **Settings → AutoPlan — Chat-сессии**: глобальный `chatSessionTaskLimit` — целое **1–10**, по умолчанию **4** (включая старые settings без поля). Значение проверяется в UI и main IPC `pilot:set-chat-session-task-limit`, сохраняется после restart; некорректное не заменяет сохранённое. Изменение лимита не меняет ON/OFF. Действует только для `experience='chat'`, подтверждённого `ACTIVE` последовательного scope при AutoPlan ON; **Work и parallel не ротируются**. OFF — ручное управление. При следующем ON учитываются уже совершённые в этом Chat DONE; новый Chat начинает счёт заново. Число N можно уменьшить/увеличить: решение принимается только на безопасной idle-паузе, busy не прерывается.
- `auto-plan-state.mjs:readChatSessionTaskProof` использует Kit `resolveReferences`, Git HEAD/историю и проверенные коммиты задач. `chat-session-rotation.mjs:advanceChatSessionTaskCounter` сохраняет для каждого Chat baseline HEAD и baseline DONE, ранее учтённые `taskId/SHA`, revision и проект/scope/session. Считаются **любые** подтверждённые DONE, включая DOCS и delivery; не считаются `task:start`, staged DONE, ответ, событие PlanMonitor, непроверенный внешний commit. Повторный snapshot, OFF→ON, restart не удваивают счёт. Переписанная история, неверный scope/owner или неоднозначный Git дают `ROTATION_PROOF_*` и блокируют автоматическую отправку, а не предполагают завершение.
- После N DONE и завершённого ответа `AutoPlan` проверяет лимит перед созданием продолжения и **повторно непосредственно перед Composer click**; достижение порога резервируется в checkpoint `rotation: reserved/notified` **до побочного действия**. Старый Chat не получает «Продолжай». Если весь план DONE, `complete` важнее ротации и новая сессия не создаётся. `rotationOperationId` строится детерминированно из проекта, scope, старого Chat и SHA границы; `WorkspaceSessions.newSession` находит уже созданную цель после перезапуска. Старые чаты и все DONE остаются.
- `ProjectAutoPlan.handoff` содержит `sourceSessionId`, `targetSessionId`, `operationId`, `kind (rotation|manual)`, `status (waiting|done|failed)` и код ошибки. При `waiting` recipient=`null`: **ни старый, ни новый Chat не могут отправлять Continue**. Новая сессия использует обычный полный Recovery `ContextSession`, собственный SessionRuntime и постоянный chatUrl. Только `delivered`, первый пригодный **idle assistant**, повторное подтверждение незавершённого Kit-плана, отсутствие Stop/Send/черновика/Review/UNKNOWN и сохранение нового recipient разрешают единственное продолжение; сохранение полномочия завершается до снятия внутреннего Send-guard. Простой select существующего Chat ничего не переносит, а явный `pilot:new-session` нового Chat при ON использует тот же handoff **без OFF→ON**. Ручное создание при OFF не включает автоматизацию.
- Невозможность создания/открытия цели, сохранения состояния, доставки Recovery или неопределённый исход Send переводят переход в `failed` с видимой причиной: **автоматического retry, второго Chat, второго Recovery или fallback в старый Chat нет**. Пользователь проверяет ситуацию и явно решает продолжение (например, OFF→ON после проверки). `enabled` может оставаться ON при заблокированном recipient. Чужой/фоновый проект не перехватывает видимый Chat; Work и parallel сохраняют прежние механизмы. Ротация — снижение риска исчерпания контекста **между задачами**, но не гарантия внутри одной длинной микрозадачи. Защита Send подробно описана в [auto-plan-send](auto-plan-send.md), Recovery — в [context-delivery](context-delivery.md), данные и runtime — в [workspace-sessions](workspace-sessions.md) / [session-runtime](session-runtime.md).

Для Send нужны подтверждённый незавершённый план, свой доступный чат с историей и ответом assistant, поле без черновика, отсутствие конфликтующего ручного Stop/Send, активной команды и другой доставки. Пауза используется один раз; checkpoint сохраняется до Send. Публикация и готовность страниц возобновляют очередь событиями; ручное сообщение пользователя приоритетнее. Технические ожидания `PLAN_UNAVAILABLE`, `PAGE_NOT_READY`, `DRAFT_PRESENT` и другие показывают `aria-pressed=true`, непустую причину `#auto-plan-message[data-reason]` и WAIT, не OFF; во время busy фаза RUNNING, разрешение остаётся ON.

Полный порядок допусков, коды ожидания, checkpoint, формат сообщения, watchdog, диагностика и защита Review — [auto-plan-send](auto-plan-send.md). Другие границы — [доставка](context-delivery.md), [живые страницы](session-runtime.md).

## Проверки

Unit проверяет A01–A06 (два основных чата, restart, stale/read error, first scope/origin, программное выключение, MANUAL_OFF, новый scope и два проекта), повторный ON восстановленной сессии, UNKNOWN, sent, Stop, черновик, Review и события гонок. Electron TEST FIXTURE проверяет реальный click в sidebar → защищённый IPC → сохранение settings → Kit/PlanMonitor → Composer: ON до публикации первого плана и ON при уже idle Recovery другого основного Work отправляют по одному продолжению без второго клика; Review WAIT, причины ожидания и отсутствие дублей проверяются отдельно. Остальные fixtures покрывают конфликт, parallel-интеграции, один финальный ответ, read-only HTTP и защищённое удаление. [Матрица A01–A06](parallel-execution-acceptance.md) отмечает границы. Живой ChatGPT, чистую ОС и native Windows принимает пользователь.

Для 0.6.114 сквозной Electron TEST FIXTURE дополнительно проверяет **N=1 и N=4**: Settings→IPC→подтверждённые Git/Kit DONE при busy→idle→новый Chat→полный Recovery из четырёх вложений→ответ assistant→единственное «Продолжай» в новом Chat; фоновый проект без смены видимого и ручной новый Chat при ON. Unit проверяет повторные проекции, restart, смену scope, foreign Git, Stop, OFF, draft, `sent/UNKNOWN`, Work/parallel и fail-closed. Эти тесты не заменяют проверку живого ChatGPT на установленном macOS и native Windows.
