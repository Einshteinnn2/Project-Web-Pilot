# Автоматическая ротация Chat-сессий по микрозадачам

## Результат

Project Web Pilot автоматически заменяет основную Chat-сессию новой после заданного количества **подтверждённо завершённых микрозадач** одного текущего последовательного плана Workflow Kit. Новая сессия получает штатный полный Recovery Context, самостоятельно подхватывает тот же checkout-план и при включённом AutoPlan продолжает работу. Цель — ограничить накопление контекста обычного Chat, у которого нет надёжного доступного Web Pilot сигнала об исчерпании контекстного окна. Это не измерение токенов и не ChatGPT auto-compact.

Пользователь выбирает в **Settings → AutoPlan → «Микрозадач на Chat-сессию»** целое число **1–10**, значение по умолчанию **4**. Значение сохраняется в локальном `settings.json` между перезапусками и действует для всех проектов на этом компьютере. Поле и краткая подсказка сообщают: «При включённом AutoPlan новая Chat-сессия создаётся после N выполненных задач. На Work не влияет». Недопустимые IPC-значения (дробные, NaN, строки вне числового поля, <1, >10) отклоняются без изменения сохранённой настройки. Отсутствующая/legacy-настройка получает 4. Настройка не включает AutoPlan самостоятельно.

Автоматическая ротация применяется **только** при `experience='chat'`, `execution_strategy='sequential'`, в подтверждённом `ACTIVE` scope и при **разрешении AutoPlan ON**. Work, parallel (включая основную и worker-сессии), проекты без плана, завершённый/архивный scope, Review без публикации и AutoPlan OFF сохраняют прежнее поведение. Новая Chat-сессия наследует обычный snapshot настроек выполнения по контракту существующего `WorkspaceSessions.newSession`, но не создаёт нового Kit-плана и не изменяет его origin или ownership.

## Пользовательский сценарий

1. В Settings установлен лимит N. Пользователь начинает план в Chat с AutoPlan ON. Web Pilot отслеживает подтверждённые DONE в **этой** Chat-сессии; во время долгой четвёртой (или N-й) задачи ничего не прерывает.
2. Kit завершает N-ю микрозадачу управляемым коммитом. Web Pilot сначала исключает следующее «Продолжай» старого чата из допуска к отправке, затем ожидает обычное окончание ответа агента (busy→idle, подтверждённая собственная пауза). Старый чат не получает повторного Send и остаётся доступным в дереве.
3. Если подтверждённый план имеет ещё незавершённые задачи, Web Pilot **однократно** создаёт новую **Chat**-сессию того же проекта штатным механизмом, открывает её в собственной записи SessionRuntime со встроенным Chromium, доставляет полный Recovery-пакет и дожидается допуска нового собственного AutoPlan после первого ответа. Новый чат получает право продолжения **без пользовательского OFF→ON**, счётчик задач начинается с нуля. Сообщение о готовности Recovery само по себе не выполняет задачу; штатный AutoPlan после этой паузы отправляет одно «Продолжай» со следующей задачей. Для фонового проекта создаётся и загружается его собственный Chat, `selectedSessionId` меняется **только внутри этого проекта**, глобально видимый проект и окно пользователя остаются прежними.
4. Если N-я задача была последней — переход отсутствует, AutoPlan завершает план прежним образом, а Kit оставляет `READY_FOR_ACCEPTANCE` до решения пользователя.
5. Если AutoPlan OFF, перехода **нет**: пользователь сам выбирает задачу/чат. При повторном ON в незавершённом плане учитываются уже подтверждённые завершения, совершённые с начала этой Chat-сессии. Ручное создание **новой** Chat-сессии при ON задаёт новую базу счёта (0) и после успешного Recovery **делает её единственным recipient AutoPlan без OFF→ON**; передача адресата блокирует старый Send. Простое выделение существующего чата не обнуляет счёт и не переносит право; при OFF ручное создание — обычная ручная операция без автоматического продолжения.

## Граница счёта и доказательства

T003: `readChatSessionTaskProof` использует `resolveReferences` Kit для Git-проверки DONE, состава коммита и зависимостей. `ProjectAutoPlan.sessions[sessionId].chatTaskCursor` хранит HEAD, базовые DONE, `taskId/SHA` и revision. Повтор не увеличивает счёт; чужая задача, переписанный Git и отсутствие доказательств дают ошибку. Авторизацию конкретного Chat проверяет Web Pilot.

T004: после idle и перед click лимит проверяется повторно. Порог сохраняет `rotation: reserved`, затем однократное уведомление (`notified`); старый Send и неизвестные повторы запрещены. Финальный DONE и Stop приоритетнее. Создание Chat/Recovery — T005–T006.

T005: операция `rotationOperationId` детерминирована по проекту, scope, старому Chat и SHA границы. `WorkspaceSessions.newSession` атомарно сохраняет `rotation` вместе с новой сессией и при повторе возвращает её же; `creationHead` защищает от изменения Git до сохранения начального счётчика. `SessionRuntimes.openRotationChat` открывает новый Chat в его собственном runtime, не меняя видимый соседний проект. `ContextSession` сохраняет попытку Recovery до Send; sent/UNKNOWN не повторяются при restart. Перенос AutoPlan recipient выполняется в T006.

T006: `ProjectAutoPlan.handoff` (waiting/done/failed) сохраняет source, target и operation ID. Пока waiting, `sessionId=null`: ни старый, ни новый Chat не могут отправлять Continue; передача в новый адрес разрешена только после `ContextSession.delivered`, постоянного URL, idle assistant, проверенного ACTIVE Kit и отсутствия Stop/Send/черновика. После сохранения нового recipient снимается внутренний Send-guard. Ручной `pilot:new-session` при ON проходит тот же переход; простой select не переносит право. Ошибка, UNKNOWN, OFF, source Stop и сбой restart оставляют план и DONE, блокируют Send, показывают причину и требуют ручного решения.

T007: Electron TEST FIXTURE для N=1 и N=4 проверяет Settings→IPC→Git/Kit DONE→busy/idle→новый Chat→четыре вложения Recovery→один Continue. Дополнительно: фоновый проект, ручной Chat при ON, отсутствие дублей. Исправлены гонки устаревшего scope и промежуточного `sending`. Обязательны `electron-smoke` и `unit-all`; живой ChatGPT и native Windows не проверяются.

- Единица счёта — одна микрозадача текущего scope с `commit_status='DONE'` и управляемым доказательством Git/Kit; **все** виды задач учитываются одинаково: T*, DOCS, DOCS-2, delivery и другие. НЕ считаются `task:start`, `plan:apply`, незавершённая транзакция, простой коммит без подтверждённого DONE, отправка «Продолжай», ответ ассистента, просмотр/переключение чата, переоткрытие, повторный PlanMonitor и задача исполнителя parallel.
- При первом пригодном наблюдении scope в своей Chat-сессии записываются `projectId`, `workspace`, `scopeId`, `sessionId`, базовое множество подтверждённых DONE/доказательств и прогресс-позиция. Для **новой** сессии база фиксируется на момент создания/передачи: уже DONE не засчитываются снова. Данные и сверяемые позиции хранятся устойчиво; после перезапуска та же сессия не становится новой и не теряет уже учтённый прогресс. Нельзя вычислять количество по DOM, числу сообщений, `continuations` или по одной изменчивой `planRevision`.
- Считать только новые подтверждённые DONE; повторная проекция не увеличивает счёт. Сверять `commit_ref` и порядок Git. При посторонней записи, смене scope, нарушенном baseline или неоднозначной истории переход **блокируется с диагностикой**, без предположений о завершении задач.
- Если пользователь меняет N при незавершённой сессии, новое значение действует с ближайшей безопасной подтверждённой idle-паузы, уже достигнутый счёт не сбрасывается. N уменьшено ниже счёта — переход при ближайшем пригодном завершении ответа, без прерывания busy; N увеличено — ожидается новый порог. Между двумя сессиями не переносить старую базу и счёт.
- Прогресс определяется состоянием плана и доказательствами Kit, а не текстом агента: завершённый ответ без commit не считается задачей; несколько DONE вследствие легитимного восстановления отображаются корректно, но внешние/неоднозначные коммиты не засчитываются молча. Транзакция, незаписанный checkpoint и read error запрещают переход и следующее Send.

## Контракт безопасной передачи

Не добавлять отдельный планировщик, polling, модельный API, отправку стартового контекста через MCP или управляющий текст агента. Расширить существующие `ProjectAutoPlan`/`project-session-auto-plan`/`AutoPlan`, события `PlanMonitor`, `WorkspaceSessions.newSession`, `ContextSession` (`src/context-session.mjs`) и `SessionRuntime` минимальным состоянием передачи. `ContextSession` подтверждает собственные фазы доставки (`delivered`, `send-unknown`, подготовка вложений, manualStart), поэтому завершение Recovery берётся из его фактического результата, а не из факта создания браузерной вкладки. Проверять через `tests/context-session.test.mjs` и `tests/session-runtime.test.mjs`. Kit является источником истины о DONE; **Web Pilot**, а не агент, создаёт новый чат и меняет получателя разрешения.

**Приоритет допусков**: на каждом idle и непосредственно перед click «Продолжай» повторно сверить scope/project/session/план/задачу, AutoPlan ON, отсутствие Review/транзакции/запрета ручного Stop/Send/черновика/UNKNOWN. После подтверждения порога запрет обычного продолжения старого чата **должен предшествовать** любому созданию новой сессии. Условие ротации и финальный `finished(plan)` проверяются в одном актуальном чтении: окончание плана важнее ротации. Не выключать пользовательский глобальный/project-level AutoPlan и не объявлять ложное `manual OFF`; старую сессию переводить в read-only для автоотправки.

**Идемпотентная передача**: ключ `[projectId, workspace, scopeId, sourceSessionId, confirmedBoundary]`; стадии `prepared → target-created → recovery-sending → ready/handed-off` либо `failed/unknown`. Журнал сохраняется до побочного действия. Повтор находит существующий Chat по operation ID, не создаёт второй. Перед передачей сверять проект, scope, ON и архив. У старого адресата Send закрывается до создания нового; Recovery и UNKNOWN не повторять, права старому автоматически не возвращать.

**Окончание подготовки**: `newSession()` и click Send не подтверждают Recovery. Нужны delivered, постоянный URL и завершённый ответ assistant своего Chat; затем единственное Continue. До этого отображается ожидание. Старый Chat не отправляет; destination ID и DONE сохраняются, история остаётся.

**Сбой**: невозможность создать/открыть новый Chat, подготовить или отправить Recovery, получить подтверждённую доставку/ответ в допустимом состоянии, сохранить ledger, подтвердить факты Kit или однозначно восстановить стадию приводит к **остановке автоматического выполнения с явной ошибкой** (без тихого fallback и без самоповтора). Сохранять полный план и все DONE, не редактировать коммиты и не удалять старые/частично созданные чаты. AutoPlan может оставаться визуально ON, но отправка заблокирована с кодом ошибки до **явного действия пользователя**; интерфейс объясняет, что проверить и как продолжить вручную. При UNKNOWN исходе Send не дублировать Recovery; возможен новый Chat только по отдельному решению пользователя. OFF во время перехода и ручной Stop немедленно блокируют новые автоматические действия, не стирая журнал неопределённого результата.

**События и гонки**: busy после commit — ждать; две проекции, два контроллера одного проекта, refresh, restart, смена выбранного проекта, Chat/Work, архивирование, изменение лимита, Manual Send/Stop, черновик, незавершённая команда и Review — не создают дублирующие чаты, не перехватывают чужой origin и не запускают Send в старой сессии. Не выполнять ротацию из `snapshot()` или рендера Settings. Точка принятия решения — сериализованное событие подтверждённого прогресса + пригодная пауза. Нет нового функционального опроса в простое.

## Проверка — пользовательский вход и автоматика

### T001 — проверяемое исходное поведение (до изменений)

- Исходный `AutoPlan` не имел лимита задач: после четырёх DONE продолжал тот же Chat. Busy не прерывался, повтор idle не отправлял дубликат. Unit-проекция не заменяет Git proof.
- Исходно новый Chat не получал recipient без OFF→ON. T006 добавит путь **новый Chat → Recovery → передача**, но простое выделение существующего чата не меняет recipient.
- Будущие сценарии ротации N=1/N=4, DOCS/delivery, restart/UNKNOWN и фонового проекта отмечены `test.todo` в двух unit suites; они **не считаются успешными тестами реализованной ротации**. Отдельно необходимо проверить живой сценарий ON до публикации → публикация → idle → автоматическое Continue: текущие изолированные fixtures не заменяют приёмку десктопного приложения.

## Границы, документы, выпуск

- Не изменять `workflow`/Kit-источник ради счётчика, не вводить сессионные планы и автоматическое создание новых планов. Не переписывать существующий `execution_origin_session_id` при ротации (исторический origin является метаданными публикации); AutoPlan recipient — отдельное поле. Не затрагивать публичные контракты трёх DOM-модулей, используемых Web Pilot Sidebar.
- Не очищать историю сообщений и не отправлять повторный полный контекст в уже начатый чат; создаётся **новая** Chat-сессия. Не удалять локальные или облачные старые чаты. Никаких скрытых переключений AutoPlan ON↔OFF и управления мышью/клавиатурой/окнами.
- Проверять готовые локальные примитивы вместо собственной очереди. Документация после реализации: `docs/modules/auto-plan.md`, `auto-plan-send.md`, `context-delivery.md`, `session-runtime.md`, `workspace-sessions.md`, `workspace-sidebar-ui.md`, `docs/architecture/OVERVIEW.md`, `README.md`, `docs/modules/release.md` при необходимости. Спецификация является рабочей до DOCS, затем постоянное поведение переносится в контракты и временный документ удаляется по правилам Kit.
- Предусмотреть полный **один** следующий выпуск **0.6.114** после T* и DOCS: source preflight/версия/проверки, единственная парная сборка macOS arm64 + Windows x64, установка готовой macOS без пересборки, публикация GitHub Release и сверка шести assets. Проверка `release-source` выполняется **в T008 перед DOCS** после перевода ожидаемой версии на 0.6.114 через `config:apply`; `codex-tools-live` также должен завершиться до DOCS. Сборка T009 не меняет `package.json` и не подменяет исходники. Git push только после DOCS; release-check evidence и version-проверки в `.harness/workflow.json` актуализировать штатным `config:apply`, не править управляемые поля вручную. Не выполнять delivery в code/test/DOCS-задачах. План остаётся READY_FOR_ACCEPTANCE до живого подтверждения пользователя.

## Требования к приёмке

Результат принят, если ротация Chat проходит всю цепочку для N=1 и N=4, выполняемые задачи остаются целыми, ни один «Продолжай» не попадает в старую сессию после подтверждённой границы, единственный Recovery появляется в новой сессии, все отключения/ошибки fail-closed, настройка переживает restart и Work/parallel не меняют поведения. Не заявлять защиту от исчерпания окна **внутри одной** микрозадачи: выбранный лимит уменьшает риск между задачами, но не измеряет контекстное окно.
