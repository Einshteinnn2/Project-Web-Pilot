# AutoPlan: включение до плана и возобновление в восстановленной сессии

## Результат

Кнопка AutoPlan управляет **разрешением выбранного проекта**, а не текущим экраном, ответом агента или моментом создания плана. После явного ON приложение самостоятельно выполняет ближайшее допустимое действие: ждёт подтверждённой публикации плана, завершения ответа, готовности страницы либо, если всё уже готово, отправляет ровно одно продолжение. Повторять OFF→ON для пробуждения запрещено. Явное OFF немедленно запрещает новые Send и запуск новых назначений; уже начатую операцию не прерывает.

Сохраняется договорённость об автоматическом OFF **только после подтверждённого завершения всего плана**. NONE, создание сессии, Recovery Context, Review, смена выбранной сессии, черновик, недоступная страница и кратковременная ошибка чтения никогда сами не выключают проектный ON. Новый план после уже завершённого и выключенного scope остаётся OFF, если пользователь вновь не включил AutoPlan.

## Воспроизведение и вероятные участки отказа

1. **ON до плана.** Включить в карточке проекта при новом Chat/Work, прочитать Recovery и опубликовать первый ACTIVE-план. В проектной записи должно сохраниться ожидание плана и затем ON его подтверждённого scope с корректным получателем. Когда агент закончит ответ о плане, начинается первый пункт без нового клика.
2. **Передача незавершённого sequential-плана.** Начать план с AutoPlan ON, явно выключить режим после части задач, открыть новую основную сессию с Recovery Context, дождаться её ответа «готов», включить AutoPlan. Выбранный новый основной чат становится адресатом продолжений текущего scope и получает первое «Продолжай» на уже готовой idle-паузе без OFF→ON.

Осмотр текущей реализации указывает на зоны риска, но не доказывает единственную причину: `ProjectAutoPlan.sync/set` разделяет `awaitingPlan`, `scopeId` и `sessionId`; `project-session-auto-plan` отдельно сопоставляет `permitted`, `PlanMonitor` и готовность страницы; `main.mjs` одновременно публикует проекцию и обрабатывает IPC переключателя. В существующем Electron smoke после публикации scope есть **повторное включение**, поэтому он не доказывает переход ON→ACTIVE без дополнительного нажатия. Точный отказ и порядок событий нужно установить диагностическими fixtures до исправления.

## Контракт состояния и запуска

- Единственный источник пользовательского разрешения — `projectAutoPlan[workspace]`, обязательно с проверкой `projectId`. Видимый `aria-pressed` и доступность отправки отражают один и тот же подтверждённый выбор; технический WAIT не маскируется под OFF. Не вводить второй переключатель, отдельную очередь-планировщик или фоновый Git polling.
- ON при `NONE` или неподтверждённом плане сохраняется как `awaitingPlan` в `settings.json` и после restart. При первой достоверной публикации scope связывается атомарно. Связь не откатывается из-за старого PlanMonitor, прежней revision, transient read error, Review-перехода или одновременной смены сессии. Новый scope не наследует ON произвольно от старого завершённого плана.
- Если при ON уже существует подтверждённый незавершённый ACTIVE-план, выбор становится действующим **в том же цикле IPC/событий**, без дополнительного пользовательского фронта. Для sequential-плана продолжает **основная сессия, в которой пользователь явно включил режим**, в том числе новая после Recovery, если Chat/Work и project identity подтверждены. Проверить, что старый чат при этом не отправляет дубликат. Простая смена выбранной сессии при ON не должна незаметно перехватывать работу; явный ON после OFF — разрешённая передача.
- Для parallel-плана адресат origin и владение `main` по-прежнему определяет опубликованный Kit-план; переключатель запускает/продолжает выдачу исполнителям, но не передаёт main чужому чату и не делает unsafe merge.
- Готовность трактуется событийно: подтверждённый scope + правильная основная сессия + доставленный Recovery/доступная страница + законченный ответ assistant + свободное поле без черновика + отсутствие Review/транзакции/ручного Send в конфликте. Включение на уже готовой паузе инициирует проверку и Send без ожидания нового DOM-события. Включение во время busy, загрузки, планирования или Recovery приводит к автоматическому пробуждению **по первому подходящему событию**.
- «Моментально» означает без искусственной повторной кнопки, интервала ожидания или нового ответа только ради пробуждения; сетевую задержку, запись checkpoint, защиту от гонки и предусмотренное 500-мс settle после busy→idle не отменять.
- Перед каждым Send повторно проверять актуальность плана, следующей задачи, документа, роли последнего сообщения и права текущей сессии. Нельзя отправить до действительного подтверждения планирования или в пустой разговор. Нельзя повторить уже подтверждённый Send, UNKNOWN или использованную паузу после повторного ON, reload, crash/restart либо двух PlanMonitor. Ledger и `AutomationSendState` остаются общими с Review.
- UI при ON и ожидании объясняет причину (`PLAN_UNAVAILABLE`, `PAGE_NOT_READY`, `USER_MESSAGE_PENDING`, `PLAN_CHANGED_OR_TRANSACTION` и т. п.); при расхождении с сохранённым разрешением показывает адресную диагностику. Сообщения агента «готов», «продолжай», «закончил» **не являются командами переключателю** и не вводятся новые текстовые маркеры.

## Матрица обязательных регрессий

Каждый сценарий должен проверять **сохранённое permission, UI `aria-pressed`, фактическое число Send/назначений, адресата, состояние плана и отсутствие второго клика**.

| Сценарий | Ожидаемый результат |
| --- | --- |
| ON в NONE → новая сессия Chat/Work → Recovery → публикация sequential-плана → assistant idle | ON сохраняется, один Send в main нового плана |
| ON во время Review PREPARED/RUNNING → PUBLISHED/ACTIVE | WAIT до публикации, затем продолжение без повторного ON |
| ON в NONE → stale NONE/read error/два PlanMonitor/restart → новая подтверждённая revision | Разрешение и правильный origin сохраняются, лишних Send нет |
| ACTIVE частично DONE → OFF → новая основная сессия → Recovery «готов» → ON | Немедленно одно продолжение в новом чате, старый молчит |
| ACTIVE частично DONE → ON до завершения ответа Recovery | Отправка после idle без новой кнопки |
| ACTIVE частично DONE → OFF/ON на уже idle-паузе | Ровно одна отправка, повторное событие не дублирует её |
| ON при busy, незагруженной странице, скрытом чате, переключении проекта, рестарте | ON не теряется; возобновление при появлении пригодной страницы/ответа |
| OFF при pending-check, между checkpoint и Composer, после ручного Send/Stop | Нового автоматического Send нет, известных отправок не дублировать |
| Draft, connection error, Review блокировка, транзакция, неподтверждённый scope | Безопасное ожидание, без OFF и без Send, затем автоматическое пробуждение |
| Отправленная/UNKNOWN пауза, возврат в старый чат, одновременные page/plan события | Не более одного Send на паузу; UNKNOWN остаётся заблокирован |
| Parallel ACTIVE: ON/OFF, несколько исполнителей, final handoff | Одна очередь, корректный origin, нет назначений при OFF и двойных merge |
| Все DONE → READY_FOR_ACCEPTANCE; другой projectId в том же пути; соседний проект | Только подтверждённое завершение переводит в OFF; нет наследования чужих прав |

## Проверка и доказательства

- Сначала повторить пользовательские цепочки на **временных fixtures**, зафиксировать порядок: IPC ON, сохранённый state, Kit-публикация, PlanMonitor, page idle/busy, разрешение конкретной сессии, попытка Send. Характеризующие тесты должны оставаться зелёными без фиктивного «двойного нажатия» в ожидаемом контракте; исправляющие assertions вводятся в соответствующих задачах.
- Unit: `tests/project-auto-plan.test.mjs`, `tests/auto-plan.test.mjs`, при необходимости `tests/plan-monitor.test.mjs` и тесты восстановления. Интеграция: Electron TEST FIXTURE **через настоящие sidebar click → preload → проверенный `pilot:auto-plan` IPC → сохранение → PlanMonitor → Composer**, включая новый Chat/Work и отправку в нужный conversation ID. Не заменять пользовательский путь одними вызовами `flow.start()`/`authorization.set()`.
- Прогнать адресные проверки, `npm test`, `npm run smoke` в выделенных задачах; тесты на macOS не объявлять живой приёмкой ChatGPT, native Windows или чистой ОС. Отдельно описать пользователю короткую живую матрицу для установленного выпуска.
- Никаких действий с реальными чатами, настройками AutoPlan пользователя, мышью/клавиатурой, его текущими проектами или данными в ходе разработки; тестировать только fixture. Не менять MCP, Claude вне разрешённого Review, модельный API, cookie или внутренние функции ChatGPT.

## Границы и поставка

Использовать существующие `ProjectAutoPlan`, `AutoPlan`, PlanMonitor, SessionRuntimes, Composer и проверенный IPC. Не менять Workflow Kit, пока причинная диагностика не установит прямой необходимости. Тесно связанные исправления выполнять последовательно в одном checkout: они меняют общую схему разрешения, адресата и отправки; parallel создаёт риск противоречивых изменений и затрудняет воспроизведение гонок.

Выпуск по обычному процессу продукта: функциональные задачи → отдельное закрепление версии/verification → DOCS → один парный build macOS/Windows → установка готового macOS app без пересборки → проверка GitHub release. Не выполнять delivery до соответствующих микрозадач. В конце оставить план READY_FOR_ACCEPTANCE до живой приёмки пользователем.
