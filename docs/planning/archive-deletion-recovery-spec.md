# Исправление зависшего удаления и потерянных исполнителей

## Результат

Project Web Pilot корректно доводит уже подтверждённое удаление после прерывания,
в том числе если каталог проекта и его карантин успели исчезнуть до обновления
журнала. Архив перестаёт показывать бесконечное «удаление ожидает завершения»,
а подтверждённо связанные записи исполнителей, их локальные сессии и служебные
ссылки исчезают вместе с завершённым удалением родителя.

Записи без родителя, для которых нельзя доказать предыдущее удаление,
**не удаляются автоматически**. В Настройках пользователь получает безопасное
адресное действие для удаления только устаревшей локальной записи исполнителя,
если его папки действительно нет. Действие объясняет, что облачные чаты
ChatGPT сохраняются; существующие файлы и активные исполнители не затрагиваются.

## Подтверждённый сценарий 11 октября 2026

- После архивирования и удаления «Мастерская файлов параллельно» в
  `workspaces.json` остались родительская запись и запись исполнителя,
  хотя обе папки отсутствовали. Два журнала `deletions/*.json`
  оставались на стадии `confirmed` при отсутствии как `workspace`, так и
  `quarantine`; повторное восстановление их не завершало.
- У «PL_Мастерская_файлов» отсутствовали родительская папка и все пять
  каталогов исполнителей. Родителя в реестре не было; пять записей
  показывались в Настройках как «Связь с родителем не подтверждена».
- В существующем `WorkspaceDeletion.finish` состояние `confirmed` при
  `missing:false` и отсутствии карантина требует `same(original, identity)`.
  `original === null` приводит к `DELETE_PATH_CHANGED`, оставляя журнал.
  `WorkspaceSessions.load` намеренно сохраняет записи с неподтверждённым
  родителем как `ownershipState:'recovery'`; у их UI нет действия очистки.
- Разовая ручная очистка состояния уже выполнена: семь записей, два журнала,
  пять устаревших циклов AutoPlan и относящиеся к ним диагностические записи
  удалены. Исходная копия сохранена вне Git в `userData/maintenance-backups/`.
  **Не повторять очистку реального профиля** и не использовать его для тестов.

## Контракт восстановления подтверждённого удаления

1. Основание для восстановления — существующий валидный журнал с точными
   `id`, `workspace`, `projectId`, `stage`, `quarantine`, зафиксированными
   `identity`, `related`, а не одно лишь отсутствие папки.
2. Матрица `confirmed`:
   - исходная папка того же dev/inode, карантина нет: повторная проверка
     отпечатка, затем прежний безопасный `rename` и удаление;
   - карантин той же identity существует: доведение удаления карантина;
   - **обе папки отсутствуют**: не выполнять никакого удаления с диска;
     при неизменившейся записи, валидном журнале и пройденных проверках
     занятости продолжить только адресную очистку локальных данных и журнала;
   - любой иной каталог, symlink, подменённая identity, повреждённый журнал,
     сменившийся projectId или неподтверждённый дочерний путь: отказ
     **без удаления** и диагностируемая причина.
3. Состояние `removing` остаётся восстанавливаемым: удаляется только
   зафиксированный карантин; новая папка по старому пути не затрагивается.
   Повтор после успеха идемпотентен. Два уже подтверждённых журнала одного
   каскада (родитель и исполнитель) должны завершаться без ложного отказа
   из-за уже удалённой записи, повторного удаления или потери соседних данных.
4. `prepareProjectRemoval` и защитный контур сохраняются: живой writer,
   read-only сервер или UNKNOWN не дают продолжать удаление; подтверждение
   пользователя само по себе не закрывает UNKNOWN. Следует различать
   `ENOENT`, недоступный том/ошибку чтения и реальную замену каталога.
5. Обновление локальных метаданных, `settings.json`, миграционных копий,
   checkpoints AutoPlan/Review/отправки, диагностики и реестра сессий
   доводится после сбоя на любом шаге. Журнал удаляется последним.

## Каскад и потерянные исполнители

- При штатном подтверждённом удалении родителя в журнал попадают
  все доказанно принадлежащие ему worktree по `parentWorkspace` +
  `parentProjectId`, assignment и Git proof. Учитываются отсутствующие
  каталоги таких исполнителей. Свежая папка, загрязнённый worktree,
  активная/UNKNOWN-команда, другое назначение или чужая идентичность
  останавливают каскад. Legacy без доказательств не считается своим.
- Завершение удаляет только точные записи и диагностические сессии этого
  каскада; соседние проекты, дочерние записи чужого родителя,
  `workspaces.json` нового `projectId` по прежнему пути и их settings
  сохраняются. Обновляется единая проекция архива и Настроек.
- Если родитель вообще отсутствует в базе **и нет доказательного журнала**,
  отсутствие папки не означает согласия удалить локальные чаты.
  Показать в блоке восстановления адресное действие «Убрать запись»
  после подтверждения пользователем. Нужны точные `{workspace,projectId}`,
  повторная проверка отсутствия папки и родителя, отсутствие pending-журнала,
  живой/UNKNOWN-команды, корректная связь с executor и неподменённое
  текущее состояние. Если проверка не пройдена — только объяснение причины.
  Действие удаляет **только локальную метаинформацию** указанного исполнителя
  и относящиеся к ней служебные следы; дисковые папки и облачные чаты
  не удаляет. Исключить массовую очистку по одной лишь строке имени.
- Повторное открытие, перезапуск и кнопка «Повторить очистку» показывают
  актуальное состояние, без зависших строк и без новых фоновых опросов.

## Проверка через пользовательский вход

Только отдельные временные fixture-проекты, реальный профиль не портить.

| Случай | Ожидаемый результат |
| --- | --- |
| `confirmed`, обе папки отсутствуют, запись неизменна | Очистка локального состояния, журнала и архива; повтор ничего не меняет |
| `confirmed`, карантин существует / оригинал существует | Прежнее безопасное продолжение по identity и fingerprint |
| `removing`, на старом пути новый каталог | Новый каталог не затронут |
| Журналы родителя и ребёнка, каталоги уже удалены | Оба журнала завершены, нет оставшихся executor-записей |
| Подмена root/child, symlink, другой projectId, повреждённый журнал | Отказ без удаления чужих файлов и записей |
| Грязный/неинтегрированный worktree, живой/UNKNOWN executor | Отказ и понятное сообщение; обхода защиты нет |
| Только потерянная запись исполнителя, его папки нет | В Настройках видна адресная очистка; после подтверждения запись исчезает |
| Папка существует, родитель заменён, операция активна | Очистка недоступна, локальные данные сохранены |
| Сбой настройки/записи/очистки диагностики и restart | Повтор доводит операцию, соседние проекты и чаты не затронуты |
| Полный Electron TEST FIXTURE через Архив и Настройки | Правильные кнопки, ошибки, изменения проекций без перезапуска |

Обязательные проверки: `project-lifecycle`, `unit-all`, `electron-smoke`;
Windows на macOS проверяется только в границах cross-package, native Windows
и живой ChatGPT подтверждает пользователь.

## Границы, реализация и выпуск

- Использовать существующие `WorkspaceDeletion`, `WorkspaceSessions`,
  `project-state-cleanup`, IPC и UI без новой службы, параллельного писателя,
  общего shell API, скрытого polling или миграции всего реестра.
- Нельзя удалять реальные проекты автоматически при старте только из-за
  `ENOENT`; без валидного журнала требуется явное действие пользователя.
  Облачные чаты, профиль Chromium, cookies, ключи и соседние workspace
  остаются нетронутыми.
- Выполнение — **sequential**, несмотря на разрешённый parallel: этапы
  меняют одно хранилище, общие функции удаления, связанные IPC и UI;
  цена согласования и опасность гонок выше выгоды независимых исполнителей.
- Целевой следующий выпуск после реализации — **0.6.112** с едиными
  macOS arm64 / Windows x64 пакетами. Сначала код и регрессия, затем
  зафиксировать версию и проверки релиза, **DOCS до delivery**, один
  `paired-release`, установка готового пакета без пересборки и GitHub
  Release. До явных delivery-задач ничего не собирать, не устанавливать
  и не публиковать. План остаётся открытым до отдельной приёмки пользователя.
